01 / 같은 목표, 다른 업무 지시

둘 다 사람이 설계합니다. 목표만 던지는 게 아닙니다.

공통 요청: “지원자의 이력서·포트폴리오와 채용공고를 근거로 면접 질문 5개, 예상 답변, 꼬리 질문, 평가 가이드를 만들어줘.”
현재 코드

업무 순서를 정한 팀

“검증 포인트를 뽑고, 질문을 만들고, 예상 답변과 꼬리 질문을 붙인 다음 평가해. 기준 미달이면 정해진 생성 경로를 다시 돌아.”

LLM은 내용 생성·평가·수정 의견을 담당.
코드가 정해진 순서와 재생성 여부를 제어합니다.

담당자들이 정해진 결재선을 따라 일합니다. 평가 담당자의 의견은 다음 작성에 반영되지만, 업무를 어디로 돌릴지는 운영 규칙이 정합니다.
학습용 제안

역할과 선택 권한을 정한 팀

“근거를 확보하고 질문을 완성해. 근거가 부족하면 조사 담당자에게, 질문 문제면 설계 담당자에게 맡겨. 검토를 통과해야 제출할 수 있어.”

LLM은 내용뿐 아니라 위임 대상·추가 조회·수정 범위도 선택.
코드가 허용 여부를 검사하고 실제 실행합니다.

팀장이 업무를 배분하고, 조사 담당자도 어떤 자료를 더 볼지 정합니다. 다만 권한, 검증 기준, 마감은 회사가 강제합니다.
설명 정정: ‘멀티에이전트’는 문헌·프레임워크마다 넓이가 다른 용어입니다. 여기서는 실제 JH를 고정 흐름 + LLM 평가·개선, 제안을 여러 역할의 LLM이 작업과 도구를 선택하는 구조로 비교합니다. 이름보다 실제 선택 권한이 핵심입니다. retry라는 값을 LLM이 직접 쓰는지 여부만으로 둘을 나누지는 않습니다.
02 / 그래프를 나란히 보기

노드와 분기는 새 설계에서도 직접 만듭니다.

종료 후 응답 구성

재생성에서도 기존 후보·리뷰를 활용합니다. predictor/driller는 보완 대상이 없으면 LLM 호출을 생략합니다. “항상 전부 처음부터 다시 생성”하는 코드는 아닙니다.

제안: 총괄이 필요한 업무를 위임

접수자료 접근 범위·목표·예산 초기화
↓
총괄 에이전트현재 결과를 보고 다음 업무 선택
↓ 선택한 action을 State에 저장
디스패처허용된 역할·입력·호출 예산 검증
↓ 선택된 담당자만 실행
근거 조사찾기·읽기·결손 보고
질문 설계생성·수정·보완
검토근거 재확인·수정 요청
↑ 담당자 결과 → 총괄이 다시 선택
완료 제안 또는 자료 확인 필요
최종 검증통과 → 제출
미달 → 수정 또는 부분 종료
사람에게 확인답변 대기·동일 실행 재개

반복·분기·종료 경로는 모두 개발자가 만듭니다. LLM은 없는 노드를 만들지 않고, 허용된 경로에 전달할 작업과 입력을 고릅니다. 예산 소진 시 코드는 강제로 부분 완료/실패 처리합니다.

‘근거 조사’ 한 노드를 열어 보면

① 조사 LLM 판단검색할까? 페이지를 읽을까?
근거를 반환할까?
② 도구 실행권한·인자 검증 후
선택한 도구 호출
③ 결과를 받은 LLM충분하면 반환
부족하면 ①에서 다시 선택

바깥에서는 에이전트 노드 하나입니다. 내부는 판단 노드와 도구 실행 노드로 만든 서브그래프입니다. 함수 안의 반복문으로 구현해도 같은 역할을 할 수 있습니다. 여기서는 이해하기 쉽게 내부도 노드로 나눴습니다.

03 / 네 명에게 무엇을 맡길까?

필요한 도구만 줍니다. 역할마다 도구 수는 달라도 됩니다.

제안의 네 에이전트는 각각 별도 역할 지침과 작업별 대화 기록을 가집니다. 같은 LLM 모델을 사용해도 됩니다. 에이전트는 담당자이고, 도구는 그 담당자가 쓰는 기능입니다.

총

총괄 에이전트 · 작업을 배분하는 팀장

목표
근거 있는 질문 5개와 준비 자료를 완성한다.
선택할 행동
delegate(role, task, refs) 근거 조사·질문 설계·검토 중 담당자에게 위임. request_input(question) 필요한 자료 확인 요청. finish 최종 제출 제안.
실행 방식
위임·확인·완료는 구조화한 action으로 반환합니다. 코드가 다른 에이전트를 호출하거나 대기·종료 경로로 보냅니다. 이 설계에서는 위임을 Tool Calling API로 포장하지 않아도 됩니다.
스스로 고르는 것
부족한 것이 근거인지, 질문 품질인지 구분하고 다음 담당자와 수정 범위를 정한다.
할 수 없는 것
직접 DB를 수정하거나 검토를 생략해 제출하지 못한다.
근

근거 조사 에이전트 · 필요한 자료를 찾는 담당자

목표
질문에 사용할 주장과 출처를 확보하고, 미확인 내용을 표시한다.
도구 2개
search_documents(query, document_ids) 허용된 지원자 문서에서 검색.
read_document(document_id, page_or_section) 선택한 원문 구간 확인.
스스로 고르는 것
어떤 키워드·문서를 볼지, 검색 결과의 앞뒤 맥락을 읽을지, 추가 조사가 필요한지.
반환
주장·인용문·문서/위치 참조를 묶은 evidence 항목, 확인하지 못한 목록. 자료가 없으면 결손을 반환한다.
할 수 없는 것
없는 포트폴리오를 도구로 만들어 오거나, 개인 자료를 인터넷에서 임의로 찾지 않는다.
설

질문 설계 에이전트 · 질문과 준비 자료를 만드는 담당자

목표
검증 포인트에 맞는 질문·예상 답변·꼬리 질문·평가 가이드를 만든다.
도구 2개
get_evidence(evidence_ids) 필요한 근거와 문맥 확인.
inspect_question_set(draft) 누락 필드·중복 ID·없는 근거 ID·동일 문구 중복을 코드로 검사.
스스로 고르는 것
새 후보를 만들지, Q3만 고칠지, 예상 답변만 보완할지 선택한다. 불충분한 근거는 질문을 확정하지 않고 근거 보완 요청으로 반환한다.
반환
생성/수정할 질문과 대상 ID, 필요한 근거 요청. 공유 State 반영은 코드가 검증한 뒤 수행한다.
할 수 없는 것
가상의 예상 답변을 지원자의 실제 발언으로 저장하지 않는다. 검사 도구는 내용의 진실성을 판정하지 않는다.
검

검토 에이전트 · 원문과 질문을 대조하는 담당자

목표
근거 없는 단정·유도 질문·중복·부실한 가이드를 찾아 수정 사항을 반환한다.
도구 2개
get_evidence(evidence_ids) 의심되는 질문의 근거 재확인.
inspect_question_set(draft) 구조와 참조 유효성 검사.
스스로 고르는 것
의심되는 근거를 추가로 읽을지, 어떤 질문·필드를 수정하도록 요구할지, 현재 버전을 통과시킬지.
반환
검토한 버전, 평가, 대상 질문 ID, 문제·수정 요청 또는 근거 부족 보고.
할 수 없는 것
질문을 몰래 수정하거나 자기 평가로 예산·필수 검증을 해제하지 않는다. 최종 제출은 코드의 검증도 거친다.
고유한 업무 도구는 총 4개입니다. 두 담당자가 같은 도구를 재사용합니다. 질문 생성·예상 답변 생성 자체는 LLM의 작업이므로 각각을 억지로 도구로 만들지 않습니다. 기존 predictor/driller 프롬프트의 목적은 질문 설계 담당자의 작업 지침으로 재사용할 수 있습니다.

문서 검색·페이지 읽기는 제안에 새로 필요한 기능입니다. 현재 JH 그래프는 이미 전달받은 문서 텍스트를 사용합니다. 비교용 문서 저장소와 위치 참조가 있다고 가정했으며, 이 기능이 현재 구현돼 있다는 뜻은 아닙니다.

04 / State는 모두 개발자가 정의

현재 State는 ‘결과와 평가’를, 제안은 ‘다음 업무’도 기록합니다.

State는 업무 장부입니다. State를 만든다고 자율성이 사라지지 않습니다. LLM이 고른 action을 어디에 기록하고, 코드가 무엇을 읽어 실행할지 정하는 설계입니다.

기록할 것현재 JH에 있는 값학습용 설계에서 유지·추가
요청·자료requested_count, job_posting, resume, portfolio, human_action, feedback유지. goal, allowed_document_ids 추가. 임의 문서 접근 방지.
검증 포인트·근거verification_profile, 질문별 document_evidenceevidence_items로 출처 ID·위치·인용문을 분리. missing_evidence로 보완 과제 기록.
질문·답변·리뷰questions, selected_questions, 점수·이슈·수정 의견·이전 리뷰기존 정보 재사용. draft_version, reviewed_version 추가. 수정 후 옛 검토 결과로 제출 금지.
다음 담당자와 업무이에 해당하는 총괄 action 객체는 없음. 그래프 엣지와 라우터가 경로를 결정.next_action = {type, role, target_ids, task, input_refs}. 총괄 LLM이 제안, 코드가 검증.
담당자의 실행 내역raw_outputs, llm_usages, 오류와 호출 로그task_results, action_log 추가. 누가 무엇을 요청하고 어떤 결과를 받았는지 기록.
반복·예산retry_count, max_retry_countremaining_model_calls, remaining_tool_calls, deadline. 코드만 차감·강제.
사람에게 질문human_action으로 생성·추가·선택 재생성 등을 요청. 그래프 내부 확인 대기는 없음.pending_question, status=awaiting_input, 체크포인트. 답변을 받은 뒤 이어가기.
담당자 작업 메모노드별 정해진 프롬프트와 출력각 서브그래프에 messages, tool_observations, task. 모든 대화를 전체 공유하지 않고 결과·참조만 공유.
예: 총괄이 role=근거조사, task=Q3의 팀 성과와 개인 기여 구분, target_ids=[Q3]를 반환하면, 코드는 이 값을 읽고 근거 조사 노드로 보냅니다. 분기 코드를 직접 작성하는 것은 지금과 같습니다.

06 / 개발자는 여전히 세부 사항을 설계

프롬프트가 제안하고, 코드가 실행 권한을 지킵니다.

총괄 프롬프트에 적을 내용

“근거 있는 면접 질문 5개를 완성한다. 근거가 부족하면 조사 담당자에게, 문항·가이드 문제면 설계 담당자에게 작업을 배분한다. 필요한 질문 ID와 문제를 함께 전달한다. 문서에 없는 지원자의 경험을 단정하지 않는다. 완성된 최신 버전을 검토받은 뒤 제출을 제안한다.”

이 지침을 읽고 LLM이 현재 상황에 맞는 action을 반환합니다.

코드로 강제할 내용

  • 역할은 근거 조사·질문 설계·검토 중 하나. action과 입력 형식을 검증.
  • 문서 ID는 현재 지원자의 허용 목록에 있어야 함.
  • 공유 결과 변경은 검증된 반환값만 반영. 질문 변경 시 검토 버전 무효화.
  • 완료 시 질문 수·필수 필드·근거 참조·최신 검토 통과 확인.
  • 학습용 상한: 실행당 모델 호출 16회, 도구 호출 12회, 담당자 호출당 도구 3회. 상한은 성능 보장이 아닌 예시.
  • 예산 소진·반복된 동일 실패는 부분 완료/실패로 종료. LLM이 더 하자고 해도 차단.
에이전트라고 해서 규칙이 사라지지 않습니다. 검토가 필수라면 경로를 코드로 강제합니다. LLM이 finish를 골랐다고 무조건 종료하는 것도 아닙니다. 사람이 준 피드백과 수정 요청도 실행 중 입력으로 받아야 합니다.
07 / 그래서 내 것과 무엇이 다른가?

담당자가 늘어난 것이 아니라, 맡긴 선택의 범위가 달라졌습니다.

비교 기준현재 JH제안
LLM의 주요 판단무엇을 질문할지, 예상 답변·꼬리 질문, 품질 평가·수정 의견기존 판단 + 누구에게 무엇을 맡길지 + 어떤 근거를 더 읽을지 + 무엇만 수정할지
다음 실행 경로고정 순서. 평가 결과와 한도를 코드가 검사해 questioner/종료로 분기허용된 담당자·도구 중 LLM이 선택. 코드가 검증·실행하며 필수 절차는 강제
재작업리뷰 피드백을 반영한 후보 보완. 필요한 항목만 enrichment할 수 있음총괄이 근거 재조사·특정 질문 수정·재검토 중 선택. 초안 버전별로 추적
개발자가 미리 만드는 것노드, 엣지, 상태, 프롬프트, 평가 기준, 재시도 규칙여전히 모두 만든다. 추가로 행동 계약·도구 권한·실행 검증·위임 계약 설계
장점과 비용경로가 예측 가능하고 테스트하기 쉽다. 이 업무에 충분할 수 있다.상황별 조사·수정 선택이 가능하다. 오선택·호출 비용·검증 부담도 증가한다.
현재: “이 순서로 일하고, 평가가 나쁘면 정해진 경로로 보완해.”
제안: “이 목표를 달성해. 사용할 담당자와 도구는 여기 있어. 다음 업무를 고르면 시스템이 검증해서 실행해.”
그러면 내 노드들도 그냥 Agent라고 부르면 안 돼?

넓은 용례에서는 역할별 LLM 노드를 에이전트라고 부릅니다. 다만 ‘각자 도구를 선택하고 계획을 바꾸는 여러 에이전트’라고 설명하면 현재 코드보다 많은 기능을 주장하게 됩니다. 현재 코드는 ‘LLM 평가와 피드백을 반영하는 워크플로우’라고 설명하면 동작이 분명합니다.

next_action 하나 추가하면 바로 멀티에이전트야?

아닙니다. 평가 점수를 retry로 바꾸어 출력하게 하는 정도라면 동작 차이가 작습니다. 이 제안에서는 총괄뿐 아니라 조사·설계·검토 담당자에게도 실제 업무 선택과 결과 확인 권한을 줍니다. State 필드 이름이 아니라 실행 중 무엇을 달리 할 수 있는지로 보세요.

항상 똑같은 업무라면 왜 이렇게 만들어?

추가 조사나 상황별 위임이 필요 없다면 현재 워크플로우가 더 단순하고 적합할 수 있습니다. 이 페이지는 멀티에이전트로 바꾸라는 권고가 아닙니다. 국책과제의 경우에는 별도로 수행계획서가 약속한 행동과 검증 기준을 맞춰야 합니다.

도구를 많이 줘야 에이전트야?

아닙니다. 하나의 검색 도구로도 키워드를 바꾸고 결과를 확인하며 추가 조회를 선택할 수 있습니다. 불필요한 도구는 줄이지, 수량을 채우려고 늘리지 않습니다. 총괄의 위임은 이 설계처럼 구조화 출력과 그래프 라우팅으로 구현해도 됩니다.
