# 면접 질문 파이프라인 품질 개선 실험일지

> **파이프라인**: `interview_graph_JH` — LangGraph 기반 면접 질문 자동 생성  
> **기술 스택**: LangGraph · LangSmith · Python · FastAPI  
> **실험 기간**: 2026-04-30 → 2026-05-06  
> **최종 결과**: 내부 루브릭 기준 **78.6 → 91.8점 (+13.2점)**

---

## 들어가며

이 문서는 두 번의 실험을 통해 면접 질문 생성 파이프라인의 품질을 끌어올린 과정을 담은 실험일지다.

**1차 실험**은 "reviewer가 retry를 시키는데 왜 품질이 수렴하지 않는가?"라는 질문에서 시작했다.  
**2차 실험**은 "품질 점수는 괜찮은데 왜 질문이 날카롭지 않은가?"라는 질문에서 시작했다.

두 실험 모두 같은 교훈을 가리켰다. **결과 로그만 봤다면 진짜 원인을 발견하지 못했을 것이다. LangSmith로 노드별 State 흐름을 직접 따라가야 비로소 보였다.**

---

## 파이프라인 구조

**1차 실험 시작 시점**
```
prepare_context → questioner → predictor → driller → reviewer → review_router
```

**2차 실험 이후 최종 구조**
```
prepare_context → verification_point_extractor → questioner → predictor → driller → reviewer → selector
```

---

## 1차 실험 — retry가 돌아도 품질이 수렴하지 않는다

### 문제 현상

`reviewer`는 `needs_revision`을 정상 반환하고, `review_router`도 retry로 정상 분기하고 있었다.  
그런데 3회 retry가 끝난 뒤에도 최종 결과에 `needs_revision` 문항이 그대로 남았다.

직관적인 첫 번째 가설은 **"retry가 실제로 실행되지 않는 것 아닌가?"** 였다.

### LangSmith로 확인한 것

`문유진 q-5` 세션의 trace를 라운드별로 추적했다.

| 라운드 | reviewer 판정 | review_router | driller 출력 |
|--------|--------------|---------------|-------------|
| 1라운드 | needs_revision (too_long_for_interview) | retry | 주당 근무시간·우선순위·정량성과 동시 요구 |
| 2라운드 | needs_revision (too_long_for_interview) | retry | 기간·근무시간·학습시간·정량성과 동시 요구 |
| 3라운드 | needs_revision (too_generic) | retry | 근무시간·야근·피로관리까지 추가 |
| 4라운드 | needs_revision (too_long_for_interview) | end | 기한·투입시간·정량결과 다시 요구 |

**reviewer는 4라운드 내내 같은 문제를 지적하고 있었다.**  
retry가 안 된 게 아니었다. `questioner`와 `driller`가 reviewer의 피드백을 실제로 흡수하지 못하고 있었다.

### 원인

`questioner`는 reviewer 피드백을 전달받았고, 실제로 반영도 하고 있었다. 매 라운드마다 질문이 짧아지거나 시간 제약이 추가된 것이 그 증거다.

문제는 그 다음이었다. **questioner가 피드백을 반영한 뒤 해당 State 필드를 초기화했다.** `driller`는 초기화된 State를 받아 실행됐기 때문에 reviewer가 무엇을 지적했는지 알지 못했고, 매 라운드마다 정량 과부하 패턴으로 회귀했다.

> **피드백이 전달도 됐고 반영도 됐다. 그런데 State 초기화로 인해 downstream 노드까지 도달하지 못했다.**

### 개선

| 항목 | 변경 전 | 변경 후 |
|------|---------|---------|
| 피드백 State 생명주기 | questioner가 반영 후 피드백 State 초기화 → driller가 피드백 미인지 | 피드백 State를 retry 루프 전체에서 보존 → 모든 downstream 노드가 참조 가능 |
| 꼬리질문 | 복수 검증포인트 동시 요구 가능 | 1문장, 1검증포인트 제약 |
| 예상답변 | 사실 단정형 서술 가능 | 가설형·추정형 유지 |
| 평가가이드 형식 | 장문 분석형 | 상/중/하 3줄 체크형 |
| issue 분류 체계 | `weak_evidence` 하나로 통합 | `doc_evidence_missing`, `followup_not_specific` 등으로 세분화 |
| 비수정 필드 보존 | partial rewrite 시 흔들릴 수 있음 | 비수정 필드 보존 규칙 추가 |
| 노드 간 의존성 | 질문 수정 후 예상답변·꼬리질문 불일치 가능 | `question_text → predicted_answer → follow_up_question` 재생성 연동 |
| reviewer 승인 기준 | 보조 산출물 이슈도 승인을 동일하게 차단 | 질문·평가가이드 중심으로 승인 판정 완화 |

### 결과와 남은 한계

일부 세션에서는 품질 수렴이 확인됐다.

```
문유진: 2승인/3수정 → 4승인/1수정 → 5승인/0수정  ✅
이서준: 4승인/1수정 → 4승인/1수정 → 5승인/0수정  ✅
최유진: 4승인/1수정 → 4승인/1수정 → 5승인/0수정  ✅
```

그러나 모든 세션이 안정적으로 수렴하지는 않았다.

```
이승현: 3/2 → 4/1 → 0/5  ← 마지막 라운드에서 오히려 악화
정지훈: 3/2 → 3/2 → 2/3
오진아: 3/2 → 1/4 → 2/3
```

reviewer 피드백 전달 구조는 개선됐지만, 피드백을 받은 driller가 다시 정량 질문 패턴으로 회귀하는 현상은 남았다.  
**이 한계가 2차 실험의 출발점이 됐다.**

## 2차 실험 — 질문은 자연스럽지만 날카롭지 않다

### 문제 현상

1차 개선 이후 전반적인 품질은 올라갔다. 그런데 AI 개발/데이터 직무 지원자 10명의 문서를 직접 검토하면서 다른 문제가 눈에 들어왔다.

> "질문이 자연스럽고 무난하다. 그런데 이 지원자 문서를 정말 깊게 읽고 뽑은 질문이라는 느낌이 없다."

면접 질문의 목적은 "좋은 지원자를 찾는 것"만이 아니다.  
**채용 후 문제가 될 수 있는 리스크를 미리 걸러내는 것** 역시 면접의 핵심 목적이다.  
그런데 생성된 질문들은 이 두 번째 역할에 약했다.

아래와 같은 검증포인트들이 질문에 충분히 반영되지 않거나, 일반론적으로만 처리되는 경우가 반복됐다.

| 리스크 유형 | 설명 |
|------------|------|
| 🔴 공백기 복귀 준비도 | 공백 사유보다 실제 복귀 행동과 산출물을 확인해야 함 |
| 🔴 직무 전환의 실행 근거 | 관심 표현이 아닌 실제 준비 산출물이 있는지 확인 |
| 🔴 정량 성과의 본인 기여 범위 | 큰 수치는 본인 직접 기여와 팀 기여를 분리해야 함 |
| 🟡 학습 vs 실무 가능성 간극 | 학습 중심 경험이 실전 적용으로 이어졌는지 확인 |
| 🟡 협업·갈등 상황에서의 실제 행동 | 갈등 유무가 아닌 조정 기준과 행동 변화로 검증 |

### 원인

`questioner`가 문서 원문을 바로 읽고 질문을 생성하는 구조였다.  
LLM은 전체 맥락을 읽었지만, **"면접에서 반드시 검증해야 할 포인트"를 먼저 정리하는 단계 없이 바로 질문을 만들었기 때문에** 날카로운 검증 질문보다 무난한 경험 확인 질문이 나오는 경향이 있었다.

또한 처음부터 최종 질문 5개에 가까운 문항을 바로 생성하는 구조라, 후보군 다양성이 제한되어 날카로운 질문이 최종 세트에 살아남기 어려웠다.

### 개선 1 — `verification_point_extractor` 노드 추가

질문 생성 전에 문서를 분석해 **"무엇을 검증해야 하는가"를 먼저 구조화하는 노드**를 새로 추가했다.

```json
{
  "must_verify_points": [
    {
      "dimension": "career_context",
      "signal_type": "return_to_work_readiness",
      "severity": "high",
      "must_ask": true,
      "why_it_matters": "공백 사유 자체보다 복귀를 위해 만든 산출물, 실무 감각 유지 방식으로 검증",
      "question_angle": "민감한 개인 사정이 아니라 복귀 준비도를 산출물 기준으로 확인"
    }
  ]
}
```

동시에 질문 생성 방식도 바꿨다.

| 항목 | 변경 전 | 변경 후 |
|------|---------|---------|
| 질문 생성 방식 | 최종 5개에 가까운 문항 바로 생성 | 검증포인트 기반 후보 10개+ 생성 |
| 최종 질문 선택 | 생성된 문항 중심 보정 | 문서 근거성·검증력 기준 상위 5개 선별 |
| reviewer 역할 | 개별 질문의 수정 필요 여부 판단 | 후보 질문 세트 전체의 품질 필터 |

### LangSmith Trace 분석 — 또 다른 State 유실 발견

최종 질문 품질을 신뢰하기 위해서는 결과만 보는 것으로는 부족하다고 판단했다.  
`verification_point_extractor`가 추출한 검증포인트가 파이프라인을 끝까지 통과해서 최종 세트에 반영되는지 확인하기 위해, `session_id: 298` (후보자: 김소현)의 trace를 직접 추적했다.

> **LangSmith run_id**: `019dfc2f-df9a-7ce0-b8ed-01daa1aa6d78`

`verification_point_extractor`가 공백기 복귀 준비도를 `must_ask: true, severity: high`로 정상 추출했고, `questioner`도 해당 질문을 생성했다.  
그런데 최종 선택 세트에서 이 질문이 탈락해 있었다.

```
verification_point_extractor
  → "공백기 복귀 준비도" must_ask = true, severity = high ✅

questioner
  → 공백기 복귀 준비 질문 생성 ✅

reviewer(1차)
  → score: 5.0 / review_status: needs_revision ⚠️  ← 선택 제외

reviewer(최종)
  → 최종 세트 탈락 ❌
```

동시에 다른 문제도 발견됐다.

```
최종 selected_questions:
  ✅ "월 60% 데이터 처리시간 단축... 본인 액션과 측정 방식 분리해 설명해 주세요."
  ✅ "월 데이터 처리시간을 60% 단축했다고 보고한 사례에서 본인 작업과 측정 방식 분리해 설명해 주세요."
                                          ↑ 동일 성과를 묻는 질문이 표현만 달리해 중복 선택됨
```

> **생성 실패가 아니라 선택 단계에서의 유실이었다.**  
> 결과 로그에는 "5개 질문이 선택됐다"고만 보인다. Trace를 따라가지 않았다면 발견하지 못했을 문제다.

### 원인 분석

**원인 1 — 중복 판정 기준이 약했다**

`selector`가 텍스트 유사도와 카테고리 수준에서만 중복을 판단했다.  
같은 `metric_anchor`(정량 성과 근거)나 `document_evidence`(문서 출처)를 기준으로 한 중복 판정이 없어, "60% 처리시간 단축"을 검증하는 질문 2개가 표현만 다른 채 함께 최종 선택됐다.

**원인 2 — must-ask 보호 단위가 너무 컸다**

must-ask 보호가 `focus_area` 수준(넓은 축)에서만 작동했다.  
`signal_type` 단위(예: `return_to_work_readiness`)까지 내려가지 않아, 공백기 복귀 질문이 `career_context` 축 전체에서 커버된 것으로 처리되어 개별 must-ask 보호를 받지 못하고 탈락했다.

### 개선 2 — Selector 로직 강화

| 항목 | 변경 전 | 변경 후 |
|------|---------|---------|
| 중복 판정 기준 | 텍스트 유사도 + 카테고리 | `document_evidence` + `metric_anchor` + `focus_area` 복합 기준 |
| must-ask 보호 단위 | `focus_area` 수준 | `signal_type` 수준으로 세분화 |
| fallback 규칙 | 없음 | must-ask 질문이 후보에 존재하면 반드시 최종 세트에 포함 |

### 결과

동일 AI 개발/데이터 직무 후보자 10명 기준, 초기 10세션과 개선 후 10세션을 비교했다.

| 지표 | 개선 전 | 개선 후 | 변화 |
|------|---------|---------|------|
| 질문 품질 평균 | 19.6 / 25 | 23.1 / 25 | **+3.5** |
| 평가가이드 품질 평균 | 19.7 / 25 | 22.8 / 25 | **+3.1** |
| **최종 품질 점수** | **78.6 / 100** | **91.8 / 100** | **+13.2** |
| 문서 근거성 | 보통~좋음 | 좋음~매우 좋음 | 뚜렷한 개선 |
| 검증력 | 보통~좋음 | 좋음~매우 좋음 | 뚜렷한 개선 |
| 면접 사용성 | 좋음 | 매우 좋음 | 개선 |

질문의 성격 자체도 바뀌었다. 초기 질문이 "경험을 들어보는 질문"이었다면, 개선 후 질문은 **"이 지원자 문서를 읽고 꼭 확인해야 할 것을 고른 질문"** 에 가까워졌다.

## 핵심 교훈

| 관점 | 배운 것 |
|------|---------|
| **LangSmith 활용** | `run_id + session_id` 기반 trace 추적으로 노드별 State 변화를 검증할 수 있다 |
| **파이프라인 디버깅** | 결과 로그만 보면 State 유실을 발견하지 못한다. intermediate state를 봐야 진짜 원인이 보인다. "반영했다"와 "끝까지 살아남았다"는 다른 문제다 |
