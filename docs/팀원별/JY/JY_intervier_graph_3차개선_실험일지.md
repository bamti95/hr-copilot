# 실험 개요

- **대상:** `interview_graph_JY`의 재시도 경로(`retry_questioner`) 부분 재생성 타깃 선정, questioner 프롬프트 구성, 라우팅 결정 관측성
- **한 줄 목적:** 재시도 시 불필요한 전체/광범위 재생성을 막고, "왜 재시도가 발생했는지"를 결과 메타데이터로 추적 가능하게 하여 latency 낮추기
- **실험 유형**: Latency / 재시도 경로 최적화 / 관측성 개선

# 문제 정의 및 관측 데이터

> 이 섹션에서는 "무엇이 문제인지"를 감이 아니라 관측된 현상으로 설명한다.
> 

### 문제 현상

- 2차 개선(Downstream 처리 대상 축소)로 1차 대비 latency는 줄었지만, 여전히 절대 latency가 높고 특히 재시도 `jy_questioner`가 큰 비중을 차지했다.
- 결과 메타데이터의 `router_decision`이 고정값이라, 실제로 `retry_driller`/`retry_questioner` 중 무엇이 선택되었는지를 실행 결과만으로 역추적하기 어려웠다.
- 재시도 최적화 방향은 "부분 재생성(최대 2개)만 수행"을 안정적으로 강제하고, questioner 입력에서 중복/불필요 컨텍스트를 줄이는 것이다.

### 설계 근거

- 재시도 경로의 비용/시간은 단순 "호출 횟수"보다, 재시도 시 어떤 범위를 다시 처리하는지(부분 재생성 강제 여부)에 크게 좌우된다.
- `existing_questions`에 재생성 대상이 포함되면, questioner가 "이미 있는 질문"과 "고칠 질문"을 동시에 고려하면서 중복 제약이 증가할 수 있다.
- 라우팅 결정값을 결과에 남기면, 다음 최적화 포인트(예: `retry_driller` vs `retry_questioner` 빈도)를 더 빠르게 좁힐 수 있다.

- 라우팅 관측성이 개선되어, 실행 결과에서 `generation_metadata.router_decision`으로 실제 재시도 분기 결정값을 확인 가능
- 재시도 `jy_reviewer` 토큰 **39.3% 감소** (7,139 → 4,331), 시간도 **29.0% 감소** (25.42s → 18.05s)

**⚠️ 기대와 달랐던 부분:**

- 전체 토큰은 2차 대비 **8.6% 증가** (65,630 → 71,283). 그럼에도 시간이 감소한 것은, 토큰만이 latency를 결정하지 않으며(제약 디코딩/모델 변동/출력 구조 영향), 재시도 경로에서의 "불필요한 제약/중복"이 줄면서 실시간이 개선되었을 가능성을 시사한다.
- LLM 호출 수가 9회에서 14회로 증가했는데, 이는 드릴러가 질문 단위 호출로 집계 단위가 세분화된 영향으로 보인다.
- 입력 토큰이 **14.8% 증가** (41,312 → 47,434)했지만, 재시도 경로에서 중복 제약이 줄면서 전체 처리 시간은 오히려 감소했다.

**🔍 주요 발견:**

- 재시도 타깃을 최대 2개로 강제하고 `existing_questions`에서 재생성 대상을 제외하는 방식은 재시도 `jy_questioner` 병목을 크게 완화했다.
- 토큰 증가에도 불구하고 시간이 감소한 것은, "불필요한 제약/중복"이 latency에 미치는 영향이 단순 토큰 수보다 클 수 있음을 시사한다.
- `router_decision`을 실측값으로 기록하면, 개선/실험 루프가 빨라지고 다음 최적화 포인트를 더 빠르게 좁힐 수 있다.
- 드릴러는 설계상 질문 단위 호출이므로, 선택 질문 수/재시도 여부에 따라 호출 항목 수가 계속 늘어날 수 있다(관측/집계 단위도 함께 정리 필요).

# 회고

### 알게 된 점

- 재시도 경로의 비용/시간은 단순 "호출 횟수"보다, **재시도 시 어떤 범위를 다시 처리하는지(부분 재생성 강제 여부)**에 크게 좌우된다.
- `existing_questions`에 재생성 대상을 포함하면, questioner가 "이미 있는 질문"과 "고칠 질문"을 동시에 고려하면서 중복 제약이 증가해 latency에 부정적 영향을 미칠 수 있다.
- 라우팅 결정값을 결과에 남기면, 다음 최적화 포인트(예: `retry_driller` vs `retry_questioner` 빈도)를 더 빠르게 좁힐 수 있다.
- 토큰 수 감소만으로는 latency 개선이 보장되지 않으며, "불필요한 제약/중복 제거"가 더 직접적인 병목 완화 요인이 될 수 있다.

### 예상과 달랐던 점

- 전체 토큰은 8.6% 증가했지만, 전체 처리 시간은 17.7% 감소했다. 이는 토큰 수보다 "중복 제약/제약 디코딩 복잡도"가 latency에 더 큰 영향을 미칠 수 있음을 시사한다.
- 재시도 `jy_questioner` 시간 감소폭(51.9%)이 다른 노드보다 월등히 컸다. 부분 재생성 강제와 `existing_questions` 제외가 매우 효과적이었다.
- 드릴러 호출 수가 세분화되면서 LLM 호출 집계 단위가 바뀌었다. 집계 방식 정리가 필요하다.

### 추가로 확인해야 할 점

- 동일 입력으로 3~5회 반복 실행해 평균 latency와 분산 비교 필요 (특히 questioner/reviewer)
- `generation_metadata.router_decision` 값과 `review_summary.quality_issues`/`approved_count`/`low_score_count`의 상관 분석
- 토큰이 증가했는데 시간이 감소한 원인 분해 (모델 변동 vs 프롬프트 구조/제약 변화)
- 드릴러 호출 집계 단위 정리 및 관측 방식 개선
- 부분 재생성(최대 2개) 강제가 최종 질문 품질이나 다양성을 낮추지 않는지 정성 평가 필요

### 한 줄 정리

> 3차 개선에서는 재시도 시 부분 재생성 타깃을 항상(최대 2개) 선정하고 questioner 입력에서 재생성 대상을 제외하여 재시도 `jy_questioner` 병목을 완화했으며, `router_decision`을 실측값으로 기록해 재시도 원인 관측성을 강화했다. 그 결과 전체 처리 시간은 284.48초로 2차 대비 17.7% 감소했고, 특히 재시도 `jy_questioner` 시간은 51.9% 감소하여 재시도 경로 최적화 효과를 명확히 확인했다.
